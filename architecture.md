# Architecture

HookedIn settles signed casino channels on Anvil (31337) or Sepolia (11155111). It uses one immutable contract, one casino writer, an independent wallet, and sandboxed game presentation. Each deployment has its own service state, signing history and wallet state.

This repository holds the parts a player has to trust: the contract, the wallet, and the protocol code both sides share. The casino service is a separate private codebase that consumes this repository as a pinned git submodule, so the service always runs an exact public protocol revision. The game SDK ([sdk/](sdk/)) and the house's games ([games/](games/)) are here too.

**HookedIn v1 is a pure prototype. Backward compatibility is not a requirement.** Contract layouts, signed messages, APIs, databases and game formats may change freely. Delete obsolete code and fields; do not retain compatibility shims, migration paths or reserved slots. Prototype deployments and saved data may be discarded when the design changes. The v1 label is not a promise that different prototype revisions interoperate. Use a fresh deployment and data for an incompatible revision.

## Design constraint

**Absolute simplicity is always a priority. Unneeded complexity must never creep in.** Keep the smallest correct implementation, reuse validation and recovery paths, and remove obsolete paths. Additional authorities, services, state and configuration need a concrete requirement. Clearly disclosed trust assumptions and manual responsibilities are acceptable. Stronger guarantees alone do not justify more protocol machinery. See [AGENTS.md](AGENTS.md).

## Boundaries

| Component                                                             | Responsibility                                                                                                                                                            |
| --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [Contract](contracts/HookedInCasino.sol)                              | Authenticate settlement, protect principal, enforce the fixed challenge window, retain claims and allocate winnings in FIFO order                                         |
| [Shared protocol](protocol/protocol.ts), [risk](protocol/risk.ts)     | Typed structures, hashes, state derivation and the admission rule, used unchanged by the wallet, the recovery tools, the games' pricing and the casino                    |
| Casino writer (private service)                                       | Admit casino bets, sign results, keep the secrets of rounds and fee accounting, keep developer bets and developers' banks, recover exact responses and owner transactions |
| [Wallet](client/wallet.ts)                                            | Authorize exact debits, verify outcomes and rejection checkpoints, save evidence before exposing results, submit settlement transactions                                  |
| [Game sessions](client/wallet-games.ts)                               | Hold the open game's in-memory spending limit and scope its operation IDs                                                                                                 |
| Game iframe ([game SDK](sdk/))                                        | Run its own rules, request casino and developer bets, read results from the receipts the wallet checked; no keys or future outcome entropy                                |
| [Recovery](protocol/recovery.ts), [watchtower](scripts/watchtower.ts) | Verify exported settlement evidence against current canonical contract state without the casino API or historical payment logs, and challenge with it                     |

Players open and fund channels directly on-chain without casino authorization. Activation verifies the confirmed deposit and channel-key authentication before retaining service state. The genesis checkpoint supports unilateral deposit recovery; randomness is not channel state at all: each casino bet names the round that settles it.

The contract settles money and nothing else: a casino bet, a debit or a credit. What an operation means (its name, the game that asked for it, what it pays into or collects from) is the hash `memo`, which the wallet and the casino check and keep and the contract never reads. A jointly signed checkpoint can establish any mutually accepted balance; one player-authorized/casino-signed transition extends it without a final player acknowledgment. EIP-712 binds name `HookedIn`, version `1`, chain and deployment. Risk admission and commission calculation belong to the casino; game interpretation belongs to the game. A casino bet is a stake paid to enter and up to 64 prizes, each paying when the round's 64-bit outcome falls in its range; prizes may overlap and then add, so one signed operation is a whole prize table: a coin flip, a Plinko board or one step of blackjack. The wallet and contract check the signed stake, every prize, the round's secret, sequence and arithmetic bounds, and the wallet records the exact return and largest payout of what the player signed. A bet and a payment also sign the game that asked for them in their memo, by its key and the developer it pays commission to, and any group the game gave them, so the game a player's money went to is part of the signed record and the casino tallies commission per game. Commission is service accounting and is absent from the signed operation. The contract reads operation/signature data from calldata, reuses computed hashes, packs status and deadline with the channel player address, and uses a transient reentrancy guard. Claim beneficiaries come from channel ownership; the claim stores only the current payout recipient. No duplicate recipient mapping is needed.

A channel holds one asset: ETH, or test coins. Test coins are the casino's own play money: a test channel is opened at the casino alone with no deposit, and its ID is a hash the contract can never produce, so nothing about it ever reaches the contract. Every account has one, and the faucet pays it 100 coins whenever it holds fewer than 10, an ordinary credit the channel signs, so an account that has deposited nothing can play at once; an account with an open ETH channel plays with its ETH unless the player chooses test coins. The casino keeps bankroll, equity, commissions, developer earnings and liabilities per asset; a round is in one asset only, and the bankroll fund takes ETH only. See [test coins](docs/protocol.md#test-coins).

## Money and authority

The deployer is the only casino owner and settlement signer. This owner controls house liquidity, including through jointly signed winning checkpoints for accounts it controls.

An open deposit is fully protected. Finalization protects `min(deposit, accepted balance)` and records the remainder as winnings debt. Gambling losses reduce the returned principal. Finalization never calls a recipient. A separate collection transaction pays protected principal and allocated winnings; a rejected transfer reverts collection and preserves the full unpaid claim. Paid totals are derived from the original amount minus remaining principal and winnings. A beneficiary can redirect collection. Every channel finalizes once.

Finalized winnings receive FIFO allocations; rejected recipients retain their allocation without preventing later cash from reaching juniors. Funding/claims allocate at most eight entries, and explicit allocation accepts at most 64. Every deposit and signed balance is below 2^128 wei, so the uint256 aggregate winnings debt cannot overflow and block unrelated finalization, whatever balances the owner signs.

House withdrawals exclude all principal and finalized winnings debt. **Active private winnings remain unsecured shared-pool obligations.** Neither replenishment nor a payout deadline is guaranteed. This is an accepted product choice; dedicated winnings collateral and per-channel payout ceilings are outside scope.

The service sets an even commission, [the edge the bankroll does not need](#settled-trade-offs), against current unreserved bankroll as a casino bet settles, which its receipt reports. Commission is operator accounting, not an additional player debit or a wallet-verified fee commitment. Half accrues to the game's developer and half to casino earnings, only for completed casino bets; a developer's own casino bet earns its developer half of its commission like any other. A developer bet is the exception: the bankroll does not back it, and the casino's part of it is what the developer's settlement gives the casino. Casino earnings stay in bankroll equity; developer payables remain separate. A developer's earnings are owed to the developer's address: the casino keeps a running tally of what that address has earned and collected, publishes every address's tally in its public status, and the developer collects it with a credit their own channel signs. Nothing on-chain moves and the bankroll does not change: money the casino already owed the developer becomes that developer's signed balance. There is no operator command and no authorization.

## State and persistence

### What the casino service promises

The service's storage, signing history and chain monitoring are internal to the private service and are not described here. What a wallet, a developer or a reviewer can rely on is its externally observable behaviour. The casino records every response it signs (an opening, a result, a rejection, a fund or bank statement, a developer's casino bet, a settlement, a close authorization) durably before that response leaves the writer, so retrying an operation ID returns the same accepted or rejected receipt, including after a restart or a restore of older service data, and a game's operation its player already carried out on another channel is declined, never carried out twice. It signs at most one outcome for a channel position and settles on each round's secret at most once; a round whose secret was lost settles nothing. A persistence failure stops new signing instead of risking a conflicting signature or a duplicate payout. New play pauses while the service's chain observation is stale and while it reconciles after a restart or a reorg; results already committed stay recoverable throughout. The service challenges stale closes of channels it knows, in its own interest: its watcher does not protect a player against the casino. It runs the exact protocol revision it pins from this repository. These are an operator's promises. The contract enforces none of them, and the wallet is built so that it does not need them: it verifies every signature, preimage and balance change itself, keeps the evidence, and can settle on-chain alone. What the wallet cannot verify is availability, liquidity and whether every requested casino bet is completed.

### Rounds

Every casino bet is on a round. The casino picks a random secret, keeps it, and names the round by its hash; a casino bet signs that name and the hash of a seed, and the outcome is a function of the secret and the seed together. Only its one secret and that one seed can settle a casino bet that signs them, and each side holds nothing but the hash of what the other picked, so a round needs no signature and the contract checks nothing about rounds but those two hashes. A round is a channel's own: the casino names it, the wallet picks the seed, the casino bet opens and closes it in one request, and the reply names the next one. It is revealed whenever it ends, also when its casino bet is declined, so the wallet records what a declined bet would have paid. Or it is a developer's: the casino names a new one whenever the developer asks, in one asset, the developer commits the hash of its seed before anybody bets on it, and the developer's own casino bet on it reveals both. See [rounds](docs/protocol.md#rounds).

### Casino bets and developer bets

A **casino bet** settles against the bankroll in the request that places it. A **developer bet** is a bet against a game's developer instead: its stake leaves the player's balance as a final debit and goes straight into the developer's bank at the casino, and the developer settles it later with a `Settlement` its own key signs, paid from that bank. Placing one trusts the developer, and the wallet says so. What a settlement pays is owed to its player and collected with a credit the wallet works out for itself, so the contract never learns that it waited; until then it is the casino's promise, outside the principal the contract protects ([trust model](README.md#trust-model)). There is no escrow, no deadline and no refund: a developer bet its developer never settles shows in the game's public record as open.

A developer bet with terms is paid what its developer says. A developer bet with prizes is provably fair: it names one of its developer's rounds, committed before the bet, so its outcome is fixed before it is placed. When betting ends, the developer places its own casino bet on the round from its bank, naming the developer bets it covers, and the round's outcome decides what each is owed: what its prizes pay if the developer's accepted casino bet covers it, and its stake back if not. Players sign their own prizes, so only bets the developer chose before the outcome existed can be owed prizes. The wallet checks the round's seed and secret, the developer's signed casino bet and its settlement, and its receipt says whether the bet was paid what it is owed, returned, or paid short. The bankroll sees a developer's hedge as what it is: one casino bet with many prizes. See [developer bets](docs/protocol.md#developer-bets).

### Risk admission

Risk admission treats a casino bet as one wager: the exact Kelly condition over the cells its ranges cut from the outcome space, which for one stake and one prize is the closed-form Kelly inequality. It reserves the bet's worst-case cash decrease plus commission synchronously across in-flight operations and makes its capacity decision before the round's secret is read, so no rejection can depend on the outcome. A developer's casino bet is admitted the same way; developer bets are not admitted at all, because the bankroll does not back them. Admission does not collateralize private balances. A casino bet requires only one operation request and no RPC reads. A wallet submits exact casino bet terms and nothing else; a rejection is the casino's signature over an unchanged-balance checkpoint one sequence above the casino bet, which the wallet verifies and countersigns on receipt through the existing result log and wallet evidence path. The casino therefore never holds a player-signed checkpoint that could supersede a result it has already completed. For a base at sequence n, the casino bet is n+1, rejection is n+2, and the next attempt is n+3. A rejection earns no commission; a lost reply stays pending until recovered. The newer proof can challenge a rejected casino bet, subject to the existing challenge deadline. The casino can selectively withhold completion without a protocol penalty; completed-result verification does not prove unbiased completion of every requested casino bet or guarantee a whole game finishes. A channel's own round is revealed with the rejection that declines its casino bet, and the wallet records what the rejected bet would have paid, so selective rejection shows on the receipt; a developer's casino bet the bankroll declines reveals its round too, and each developer bet it named is returned with what it would have paid on its receipt. The wallet countersigns a declined casino bet on its channel's own round only with that round's secret, or when the casino says it lost the round, which the receipt then says in words. The rule itself is [protocol/risk.ts](protocol/risk.ts); see [economics](docs/economics.md).

### Chain reads

Chain reads use canonical block hashes and reject a changed observation ([protocol/chain-observer.ts](protocol/chain-observer.ts)). HTTP RPC transports time out after ten seconds; a late response cannot resume a failed read. Sepolia requires two independently selected RPCs, fresh progressing heads and confirmation depth; Anvil allows on-demand mining. The wallet, the watchtower and the service share this observer.

### The wallet

The wallet uses IndexedDB for funding/channel keys, signed requests, receipts and transaction intents; nothing about games. Injected funding keys stay in the external wallet. Web Locks and durable revisions serialize competing tabs. Each channel owns its pending operation across reorgs and selection changes; registration recovery is derived from its on-chain status. Funding keys commit before their receiving address is displayed. Small settings use Web Storage.

A game's spending limit is a reservation against the signed channel balance held only in the open tab's memory. The player sets it in the wallet's dialog, when the game asks or from the top bar; leaving the game, reloading or closing the tab releases it, and the money was in the channel all along. Bets and payments are limited to it; verified profits raise it. The limit signs nothing, so the player sets it while an operation is pending too, up to the balance less what that operation has already committed. A result recovered after a reload changes only the channel balance. A game's operation IDs belong to the player, the asset and the game, not to a channel, so exact retries and receipt lookups by the game's own IDs work across the player's channels without wallet-side game records, and the casino declines an ID its player already used on another channel rather than carry it out twice. No contract or server game account is required.

Encrypted backups contain **only the selected account**: its local funding key, channel keys, evidence, close authorizations and exact pending operations. Back up each account separately. Keys alone cannot reconstruct private signed balances. Backups and transaction journals must match the supported schema and deployment. The wallet retains up to 100 recent activity receipts. Active-channel observations commit under the action lock; bankroll hints and bounded historical reads run outside it. Optional reads merge under the existing lock into the latest durable revision, updating only unchanged historical records for the same account. Bankroll information and activity commit independently, so slow optional reads still make progress across active-channel polls. Failures are shown as stale activity, and a persistence failure blocks waiting actions as well as new ones. Execution retries compare every caller-supplied term against the saved operation; receipt lookup is explicit. Every transaction journal latches failed persistence and requires a restart from durable state before any further action; journals retain only the pending transaction and latest completion. See [the wallet](docs/frontend.md).

### Games

A manifest states what the wallet will hold a game to. No game states what it pays back: a figure a game promises is unverifiable, because nothing bounds how often a game wagers the money it holds, so a game that promised 99% could still churn a balance away. What a player gets instead is measured: the wallet computes the exact return of every bet it signs, from that bet's own prize table, and shows it against the bet in their history, and the casino publishes the same figure for every bet placed in a game. A game's developer bets are settled by its developer's key. Every bound a game must respect — the prizes one bet holds, the size of the outcome space, the developer bets one casino bet of its developer covers, how large a developer bet's terms and a group may be — is part of the protocol revision: `wallet.hello` reports them, and `GET /api/config` the same numbers to a developer, so a game reads them rather than carrying copies.

Games own rules, state transitions and persistence: the iframe keeps its host's origin (`allow-scripts allow-same-origin`) and stores its rounds there, keyed by the player's name and the asset in play. The wallet never frames its own origin and its host forbids framing outright. Each game is its own site, known by its key, made from its developer and the name they published it under in their own profile at the casino (`@alias/game` or `~uname/game`; [catalog.json](catalog.json) names the house developer and what `@hookedin` publishes). The developer is the account that publishes it: it earns the game's commission, its bank takes the stakes of the game's developer bets and its key settles them, so a game's server holds everything that account holds. The wallet refuses a game whose manifest names another developer. Where a game is served can change while its key stays, so a game keeps its history. Each runs its own rules inside its iframe: a one-shot game places its whole prize table as one casino bet, and a sequential game places [one casino bet per step](#settled-trade-offs), priced with the casino's own admission rule. The wallet signs and verifies each bet whole, and a game reads what to show from its receipt; developers remain responsible for how steps combine into their advertised game. A game with a server ships page and server as one Cloudflare Worker on one origin: static assets, and a Durable Object under `/api/`. The casino deployment runs no game servers. Storage failure stops further operations until durable restoration. A game learns one thing about who is playing: their uname, derived from an address the casino never discloses, with the alias they are shown by beside it. Their address, their channel and their balances never cross the bridge. Game developers test against [testing/game-wallet.ts](testing/game-wallet.ts), a real wallet wired to an in-memory casino stub that holds every casino bet to the casino's own admission rule; [testing/conformance.ts](testing/conformance.ts) is one behaviour suite this repository runs against the stub and the casino service against itself, so the stub behaves as the casino does wherever a game depends on it. See the [game SDK](sdk/).

### The bankroll fund

The bankroll is open to investors. A player transfers money from a channel into the bankroll fund and holds shares of it, priced by the bankroll's equity; selling shares owes the player their worth, collected with a credit the player's own channel signs. It is a trust arrangement and says so: the casino states the price and could take the money. What the design guarantees is accountability. Every change to a holding is a statement the casino signs and the wallet verifies against the holder's own signed transfer or redemption, all of it lives in the signing history, and the owner's own funding and withdrawals trade house shares at the going price, so taking more than the house owns is visible in the signed public state of the fund. It is deliberately not a token: shares cannot be transferred, nothing new is on-chain, and the contract is unchanged. See [the bankroll fund](docs/protocol.md#the-bankroll-fund).

## Settled trade-offs

These are chosen on purpose and stay chosen; [AGENTS.md](AGENTS.md#settled-decisions) asks that they not be reopened.

**Commission is the edge the bankroll does not need.** A casino bet is admitted when the bankroll can take it with no commission at all; commission is then the most that still leaves the bankroll's residual wager Kelly-sound, split equally between the game's developer and the casino. The calculation is more involved than a fixed rate, and that is the point: a fee taken first would shrink every bet the bankroll can take, while this admits the largest ones and charges only the surplus. A game sets its own tables, and its developer earns half of the edge they carry. Nothing here pretends to protect a player from a game: any game can waste the money it is given on bets that pay back little, whatever the fee, and a cap would only hide that. The player's protection is the spending limit they set, and the measured return of every bet, which the wallet records and does not enforce.

**A multi-step game is a sequence of casino bets.** Every step is one casino bet, settled on its own, so the bankroll moves atomically with each step and no step waits on another. A player can walk away after any settled step with the cash that step left them; nothing makes them finish a hand. A game built this way is a series of casino bets, each admitted and charged by itself, not a committed hand, and its prices follow from that.

**A developer's solvency is outside HookedIn.** A developer's bank reserves nothing, and a settlement is paid from it only as far as it can pay. Whether a developer can pay what its developer bets are owed, and proving it, is between the developer and its players; the casino does not attempt it. Playing a developer's game trusts that developer: for its tables in any game, and with a developer bet for its payment, and for its outcome too when the bet has terms.

## Recovery and manual responsibility

Either party can start unilateral close. Anyone with strictly newer supported evidence can challenge before the fixed 24-hour deadline; challenges never extend it. After the deadline anyone can finalize or trigger collection. Immediate cooperative close requires the funding account and casino; all signatures are EOA signatures, so a contract account funding a channel exits through unilateral close.

**Users must monitor their channel and get a stale-close challenge mined before the deadline.** The UI shows observation time, saved/proposed sequence, balance at risk, deadline and pending challenge, plus principal, unpaid winnings and allocated winnings. Merely opening the wallet does not send a challenge. A 0.001 ETH reserve is a convenience floor, not a guaranteed gas budget. An independent watchtower is optional: `npm run watchtower` watches one exported evidence file and challenges with it from a separately funded relayer key. The casino's watcher does not protect against a malicious casino.

A default recovery bundle contains the on-chain opening identity and minimal supported proof, with no private keys, game data or pricing payload. A single independently chosen RPC can verify registered identity and current claim state. Inspection never requests payment logs. Historical inspection requires state at the requested block, and cannot guarantee that block survives future reorgs. Game state is not needed to settle a channel. See [recovery](docs/request-evidence.md).

## Release

The wallet ships exactly one runtime pin, [client/contract-artifact.ts](client/contract-artifact.ts). Ordinary compilation checks it without replacing it; `npm run release:artifact` explicitly updates it after source review. The contract is compiled without a metadata hash, so the pin moves only when the compiled code does: a comment or a name changes nothing that is deployed. Recovery runs the archived artifact without compiling. Compilation is not evidence of independent review. `npm run build` writes the wallet to `dist/` as one readable `main.js` with its source map, `vendor/ethers.js` byte-identical to the npm release of ethers, and `config.js` with the deployment's settings, so each can be checked on its own. `npm run audit:package` archives source, lockfile, compiler input/output, runtime pin, a hashed manifest and any validation reports together. Protect wallet release credentials separately from casino hosting: the wallet is a static site that shares nothing with the service but the public protocol. Host fencing, storage-loss, stale-restore, nonce, RPC and key-loss drills belong to the operator of the private service. Tests establish software behavior, not production infrastructure independence or a third-party security audit; no third-party audit has taken place.
