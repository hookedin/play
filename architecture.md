# Architecture

HookedIn settles signed casino channels on Anvil (31337) or Sepolia (11155111). It uses one immutable contract, one casino writer, an independent wallet, and sandboxed game presentation. Each deployment has its own service state, signing history and wallet state.

This repository holds the parts a player has to trust: the contract, the wallet, and the protocol code both sides share. The casino service is a separate private codebase that consumes this repository as a pinned git submodule, so the service always runs an exact public protocol revision. Games and the game SDK live in their own public repositories.

**HookedIn v1 is a pure prototype. Backward compatibility is not a requirement.** Contract layouts, signed messages, APIs, databases and game formats may change freely. Delete obsolete code and fields; do not retain compatibility shims, migration paths or reserved slots. Prototype deployments and saved data may be discarded when the design changes. The v1 label is not a promise that different prototype revisions interoperate. Use a fresh deployment and data for an incompatible revision.

## Design constraint

**Absolute simplicity is always a priority. Unneeded complexity must never creep in.** Keep the smallest correct implementation, reuse validation and recovery paths, and remove obsolete paths. Additional authorities, services, state and configuration need a concrete requirement. Clearly disclosed trust assumptions and manual responsibilities are acceptable. Stronger guarantees alone do not justify more protocol machinery. See [AGENTS.md](AGENTS.md).

## Boundaries

| Component                                                             | Responsibility                                                                                                                                         |
| --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| [Contract](contracts/HookedInCasino.sol)                              | Authenticate settlement, protect principal, enforce the fixed challenge window, retain claims and allocate winnings in FIFO order                      |
| [Shared protocol](protocol/protocol.ts), [risk](protocol/risk.ts)     | Typed structures, hashes, state derivation and the admission rule, used unchanged by the wallet, the recovery tools, the games' pricing and the casino |
| Casino writer (private service)                                       | Admit risk, sign results, keep the secrets of rounds and fee accounting, recover exact responses and owner transactions                                |
| [Wallet](client/wallet.ts)                                            | Authorize exact debits, verify outcomes and rejection checkpoints, save evidence before exposing results, submit settlement transactions               |
| [Game sessions](client/wallet-games.ts)                               | Hold the open game's in-memory spending limit and scope its operation IDs                                                                              |
| Game iframe ([game SDK](https://github.com/hookedin/game-sdk))        | Run its own rules, request atomic bets, read results from verified outcomes; no keys or future wager entropy                                           |
| [Recovery](protocol/recovery.ts), [watchtower](scripts/watchtower.ts) | Verify exported settlement evidence against current canonical contract state without the casino API or historical payment logs, and challenge with it  |

Players open and fund channels directly on-chain without casino authorization. Activation verifies the confirmed deposit and channel-key authentication before retaining service state. The genesis checkpoint supports unilateral deposit recovery; randomness is not channel state at all: each bet names the round that settles it.

The contract supports bet, payment, transfer debit and incoming credit transitions. A jointly signed checkpoint can establish any mutually accepted balance; one player-authorized/casino-signed transition extends it without a final player acknowledgment. EIP-712 binds name `HookedIn`, version `1`, chain and deployment. Risk admission and commission calculation belong to the casino; game interpretation belongs to the game. A bet is a stake paid to enter and up to 64 prizes, each paying when the round's 64-bit outcome falls in its range; prizes may overlap and then add, so one signed operation is a whole prize table: a coin flip, a Plinko board, a player's roulette chips or one step of blackjack. The wallet and contract check the signed stake, every prize, the round's secret, sequence and arithmetic bounds, and the wallet records the exact return and largest payout of what the player signed. Operations contain only current wager, payment and transfer fields. Commission is service accounting and is absent from the signed operation. The contract reads operation/signature data from calldata, reuses computed hashes, packs status and deadline with the channel player address, and uses a transient reentrancy guard. Claim beneficiaries come from channel ownership; the claim stores only the current payout recipient. No duplicate recipient mapping is needed.

## Money and authority

The deployer is the only casino owner and settlement signer. This owner controls house liquidity, including through jointly signed winning checkpoints for accounts it controls.

An open deposit is fully protected. Finalization protects `min(deposit, accepted balance)` and records the remainder as winnings debt. Gambling losses reduce the returned principal. Finalization never calls a recipient. A separate collection transaction pays protected principal and allocated winnings; a rejected transfer reverts collection and preserves the full unpaid claim. Paid totals are derived from the original amount minus remaining principal and winnings. A beneficiary can redirect collection. Every channel finalizes once.

Finalized winnings receive FIFO allocations; rejected recipients retain their allocation without preventing later cash from reaching juniors. Funding/claims allocate at most eight entries, and explicit allocation accepts at most 64. Every deposit and signed balance is below 2^128 wei, so the uint256 aggregate winnings debt cannot overflow and block unrelated finalization, whatever balances the owner signs.

House withdrawals exclude all principal and finalized winnings debt. **Active private winnings remain unsecured shared-pool obligations.** Neither replenishment nor a payout deadline is guaranteed. This is an accepted product choice; dedicated winnings collateral and per-channel payout ceilings are outside scope.

The service calculates an even commission against current unreserved bankroll and reports it in the receipt. Commission is operator accounting, not an additional player debit or a wallet-verified fee commitment. Half accrues to the developer and half to casino earnings, only for completed bets. Casino earnings stay in bankroll equity; developer payables remain separate. Developer payouts are cash-only owner withdrawals with single-use IDs.

## State and persistence

### What the casino service promises

The service's storage, signing history and chain monitoring are internal to the private service and are not described here. What a wallet, a host or a reviewer can rely on is its externally observable behaviour. The casino records every response it signs (an opening, a result, a rejection, both legs of a transfer, a buy-in, a fund statement, a close authorization) durably before that response leaves the writer, so retrying an operation ID returns the same accepted or rejected receipt, including after a restart or a restore of older service data. It signs at most one outcome for a channel position and settles on each round's secret at most once; a round whose secret was lost settles nothing. A persistence failure stops new signing instead of risking a conflicting signature or a duplicate payout. New play pauses while the service's chain observation is stale and while it reconciles after a restart or a reorg; results already committed stay recoverable throughout. The service challenges stale closes of channels it knows, in its own interest: its watcher does not protect a player against the casino. It runs the exact protocol revision it pins from this repository. These are an operator's promises. The contract enforces none of them, and the wallet is built so that it does not need them: it verifies every signature, preimage and balance change itself, keeps the evidence, and can settle on-chain alone. What the wallet cannot verify is availability, liquidity and whether every requested wager is completed.

### Rounds

Every bet is on a round. The casino draws a secret, keeps it, and names the round by its hash; a bet signs that name and a seed, and the outcome is a function of the secret and the seed together. The name is fixed before the seed exists and only its one secret can settle a bet that signs it, so a round needs no signature, and the contract checks nothing about rounds but that hash. The usual round is the channel's own: the casino names it, the wallet draws the seed, the bet opens and closes it in one request, and the reply names the next one. A hosted round lets up to 256 channels share one outcome: a game's host, any key with no channel and no money, asks for a round, opens it with a seed of its choosing, each player's own wallet joins it with its bet, and the host closes it, at which point one signing-history record reveals the secret and settles every seat. Seats are admitted one at a time against the whole round; a player gives up a seat at the cancel endpoint, which returns the ordinary rejection checkpoint, or the recorded result if the host closed the round first. A round is revealed whenever it ends, also when it is declined or left open too long, so the wallet records what a declined bet would have paid. Host and casino together could choose a hosted round's outcome; neither can alone, so the wallet asks the player before an open game may place a hosted bet and marks those receipts. See [rounds](docs/protocol.md#rounds).

### Risk admission

Risk admission treats a round as one wager: the exact Kelly condition over the cells its ranges cut from the outcome space, which for one stake and one prize is the closed-form Kelly inequality. It reserves the round's worst-case cash decrease plus commission synchronously across in-flight operations, admits or declines the list as a whole, and makes its capacity decision before the round's secret is read, so no rejection can depend on the outcome. A hosted round is admitted again as a whole with each seat that joins; a seat that does not fit is declined alone, and one that was admitted is settled. It does not collateralize private balances. Normal bets require only one operation request and no RPC reads. A wallet submits exact wager terms and nothing else; a rejection is the casino's signature over an unchanged-balance checkpoint one sequence above the wager, which the wallet verifies and countersigns on receipt through the existing result log and wallet evidence path. The casino therefore never holds a player-signed checkpoint that could supersede a result it has already completed. For a base at sequence n, the bet is n+1, rejection is n+2, and the next attempt is n+3. A rejection earns no commission; a lost reply stays pending until recovered. The newer proof can challenge a rejected wager, subject to the existing challenge deadline. The casino can selectively withhold completion without a protocol penalty; completed-result verification does not prove unbiased completion of every requested wager or guarantee a whole game finishes. A declined round is revealed, with the rejection or when its host closes it, and the wallet records what the rejected wager would have paid, so selective rejection shows on the receipt. The rule itself is [protocol/risk.ts](protocol/risk.ts); see [economics](docs/economics.md).

### Chain reads

Chain reads use canonical block hashes and reject a changed observation ([protocol/chain-observer.ts](protocol/chain-observer.ts)). HTTP RPC transports time out after ten seconds; a late response cannot resume a failed read. Sepolia requires two independently selected RPCs, fresh progressing heads and confirmation depth; Anvil allows on-demand mining. The wallet, the watchtower and the service share this observer.

### The wallet

The wallet uses IndexedDB for funding/channel keys, signed requests, receipts and transaction intents; nothing about games. Injected funding keys stay in the external wallet. Web Locks and durable revisions serialize competing tabs. Each channel owns its pending operation across reorgs and selection changes; registration recovery is derived from its on-chain status. Funding keys commit before their receiving address is displayed. Small settings use Web Storage.

A game's spending limit is a reservation against the signed channel balance held only in the open tab's memory. The player sets it in the wallet's dialog, when the game asks or from the top bar; leaving the game, reloading or closing the tab releases it, and the money was in the channel all along. Wagers and payments are limited to it; verified profits raise it. A result recovered after a reload changes only the channel balance. Operation IDs are scoped by channel and game so exact retries and receipt lookups by the game's own IDs work without wallet-side game records. No contract or server game account is required.

Encrypted backups contain **only the selected account**: its local funding key, channel keys, evidence, close authorizations and exact pending operations. Back up each account separately. Keys alone cannot reconstruct private signed balances. Backups and transaction journals must match the supported schema and deployment. The wallet retains up to 100 recent activity receipts. Active-channel observations commit under the action lock; bankroll hints and bounded historical reads run outside it. Optional reads merge under the existing lock into the latest durable revision, updating only unchanged historical records for the same account. Bankroll information and activity commit independently, so slow optional reads still make progress across active-channel polls. Failures are shown as stale activity, and a persistence failure blocks waiting actions as well as new ones. Execution retries compare every caller-supplied term against the saved operation; receipt lookup is explicit. Every transaction journal latches failed persistence and requires a restart from durable state before any further action; journals retain only the pending transaction and latest completion. See [the wallet](docs/frontend.md).

### Games

Games own rules, state transitions and persistence: the iframe keeps its host's origin (`allow-scripts allow-same-origin`) and stores its rounds there, keyed by player and channel. The wallet never frames its own origin and its host forbids framing outright. Each listed game is its own site, named by an absolute manifest URL in [catalog.json](catalog.json), and runs its own rules inside its iframe: a one-shot game places its whole prize table as one bet, and a sequential game places one bet per step, priced with the casino's own admission rule. The wallet signs and verifies each bet whole, and a game reads what to show from the verified outcome; developers remain responsible for how steps combine into their advertised game. A game with a server ships page and server as one Cloudflare Worker on one origin: static assets, and a Durable Object under `/api/`. The casino deployment runs no game servers. Storage failure stops further operations until durable restoration. Game developers test against [testing/game-wallet.ts](testing/game-wallet.ts), a real wallet wired to an in-memory casino stub; see the [game SDK](https://github.com/hookedin/game-sdk).

### Tables

Players can play against each other at a table. A table is its terms: a host key, the developer, a deadline and a nonce, whose hash is the table's ID. A player buys in with a transfer naming that ID, sent by their own wallet, and may top up until the deadline; the host is not asked. The amount joins the table's pot in the casino's escrow and the channel is free at once. The host signs numbered settlements that pay players out of the pot and take a rake, split between the developer and the casino. The casino checks only that the host signed, that every paid player bought in and that no more leaves the pot than came in, so the host shares the pot however its game decides, which is what poker needs. At the deadline the casino returns what is left to the players still owed their buy-in. Each wallet verifies a payout against the host's signature, or against the passed deadline, before collecting it. No developer holds money and the host can pay only players who bought in, but money on a table is the casino's promise, outside protected principal. A game's server learns who is playing from an `Identity` the wallet signs with its channel key over the game page's origin and the server's nonce; it authorizes nothing at the casino. The reference hosts are [poker](https://github.com/hookedin/poker), no-limit hold'em, and [rock paper scissors](https://github.com/hookedin/game-rps), built on the [game SDK](https://github.com/hookedin/game-sdk)'s host kit. See [tables](docs/protocol.md#tables).

### The bankroll fund

The bankroll is open to investors. A player transfers money from a channel into the bankroll fund and holds shares of it, priced by the bankroll's equity; selling shares owes the player their worth, collected like a table's payout. It is a trust arrangement and says so: the casino states the price and could take the money. What the design guarantees is accountability. Every change to a holding is a statement the casino signs and the wallet verifies against the holder's own signed transfer or redemption, all of it lives in the signing history, and the owner's own funding and withdrawals trade house shares at the going price, so taking more than the house owns is visible in the signed public state of the fund. It is deliberately not a token: shares cannot be transferred, nothing new is on-chain, and the contract is unchanged. See [the bankroll fund](docs/protocol.md#the-bankroll-fund).

### Transfers

Games can transfer allocated money to their manifest's developer, who uses an ordinary channel to accept payments and pay players back. Developers control their game rules and payouts; HookedIn provides no arbitration or refund guarantee. The recipient wallet accepts each credit at its own next position, preserving the single pending operation rule. The sender can withdraw an unaccepted offer with the ordinary rejection checkpoint and keep playing without closing. The writer records both signed legs in one record and commits their balances together. Each leg settles independently, relying on the existing casino authority for matching debit/credit accounting. Transfers retain the original principal and shared-pool liquidity rules. Incoming payments enter unallocated wallet balance, never enabling or replenishing a game automatically. See [transfers](docs/protocol.md#transfers).

## Recovery and manual responsibility

Either party can start unilateral close. Anyone with strictly newer supported evidence can challenge before the fixed 24-hour deadline; challenges never extend it. After the deadline anyone can finalize or trigger collection. Immediate cooperative close requires the funding account and casino; all signatures are EOA signatures, so a contract account funding a channel exits through unilateral close.

**Users must monitor their channel and get a stale-close challenge mined before the deadline.** The UI shows observation time, saved/proposed sequence, balance at risk, deadline and pending challenge, plus principal, unpaid winnings and allocated winnings. Merely opening the wallet does not send a challenge. A 0.001 ETH reserve is a convenience floor, not a guaranteed gas budget. An independent watchtower is optional: `npm run watchtower` watches one exported evidence file and challenges with it from a separately funded relayer key. The casino's watcher does not protect against a malicious casino.

A default recovery bundle contains the on-chain opening identity and minimal supported proof, with no private keys, game data or pricing payload. A single independently chosen RPC can verify registered identity and current claim state. Inspection never requests payment logs. Historical inspection requires state at the requested block, and cannot guarantee that block survives future reorgs. Game state is not needed to settle a channel. See [recovery](docs/request-evidence.md).

## Release

The wallet ships exactly one runtime pin, [client/contract-artifact.ts](client/contract-artifact.ts). Ordinary compilation checks it without replacing it; `npm run release:artifact` explicitly updates it after source review. Recovery runs the archived artifact without compiling. Compilation is not evidence of independent review. `npm run build` writes the wallet to `dist/` as one readable `main.js` with its source map, `vendor/ethers.js` byte-identical to the npm release of ethers, and `config.js` with the deployment's settings, so each can be checked on its own. `npm run audit:package` archives source, lockfile, compiler input/output, runtime pin, a hashed manifest and any validation reports together. Protect wallet release credentials separately from casino hosting: the wallet is a static site that shares nothing with the service but the public protocol. Host fencing, storage-loss, stale-restore, nonce, RPC and key-loss drills belong to the operator of the private service. Tests establish software behavior, not production infrastructure independence or a third-party security audit; no third-party audit has taken place.
